# Model duplication, 11 Oct 2026

Follows `261008-review.md`. The `TODO.md` items from that review are done, but in services, not in the schema. Each duplicated idea still has more than one stored record. Service code copies writes between them. Where a writer skips the copy, the records disagree.

## Proposals

| Priority | Change | Tables | Removes | Status |
| --- | --- | --- | --- | --- |
| High | Derive quote status | `quote.status` dropped | 6 writers, the sync code, 4 drift paths | Done |
| High | One price target | `price_alert` + `watchlist` -> `price_target` | 1 table, 1 service (~190 lines), 1 TUI tab, 1 CLI noun | Done |
| Low | Drop `quote.currency` | `quote.currency` dropped | a column that is always `USD` | Done |
| Low | Notes in one place | `watchlist.notes` folds into `note` | merges with the price target | Done, with 2 |

Not proposed:

- Classification. `ProductService.report_classification` derives one label at read time from category, then spec name, then tags. Nothing is stored twice.
- `purchase_order.vendor_id`, `product_id` and `unit_price` when `quote_id` is set. These snapshot what was paid. A later quote edit must not change spend.

## 1. Derive quote status (High)

`quote.status` stores a value that two other records already determine:

- `ordered` / `received`: the quote has an active purchase order (`PurchaseOrderService.active_for_quote`).
- `considering`: the quote is on a purchase list.

Six places write the column: `QuoteService.set_status`, `QuoteService.update`, `PurchaseListService._sync_considering`, `PurchaseListService.ensure_considering`, and the two branches of `set_status` that call `PurchaseOrderService.ensure_for_quote`. `PurchaseOrderService.update_status` and `create_from_quote` do not write it.

Drift found by reading the code:

1. `buylog po update quote-1 --status cancelled` leaves the quote `ordered`. `might_buy` filters on status, so the quote is not listed, and the TUI still shows it as Ordered.
2. `buylog po update quote-1 --status received` leaves the quote `ordered`.
3. `buylog po create PO-1 --from-quote 7` records a purchase, but quote 7 keeps its old status.
4. `QuoteService.update(status=...)` sets the column without creating an order or a list entry.

Change:

- Drop the column. `Quote.status` becomes a read-only `hybrid_property`:
  1. An active (not cancelled) order: `received` if the order is received, otherwise `ordered`.
  2. Otherwise, on any purchase list: `considering`.
  3. Otherwise `None`.
- Queries filter on the hybrid's SQL expression instead of the column: `QuoteService.get_by_status`, `PurchaseListService.might_buy`, `ReportService.purchase_summary_report`.
- `QuoteService.set_status` stays as the command. It writes only the order or the list membership.
- Delete `_sync_considering` and the `status` parameter of `QuoteService.update`.

Migration, in order:

1. For each quote marked `ordered`/`received` with no active order, call `ensure_for_quote`.
2. For each quote marked `considering` that is on no list, add it to Considering.
3. Drop the index on `quote.status`, then drop the column. `ALTER TABLE ... DROP COLUMN` (SQLite 3.35+) refuses an indexed column. `vendor_website_statements` in `migrate.py` is the pattern to follow.

Trade-off: the TUI quotes table reads status for every row. Without `selectinload` on orders and lists, that is 2 queries per row.

Done as proposed, plus:

- Migration step 1 is SQL, not `ensure_for_quote`, because `migrate.py` runs statements. It uses the same pricing, and `test_migration_prices_an_order_like_ensure_for_quote` pins that. It creates an order only when the quote has no order at all, not merely no active one. A quote whose only order is cancelled was stored as `ordered` because of drift 1, and recreating its order would undo the cancel.
- A `pending` or `approved` order derives `ordered`. Spend already counts those orders, so the quote reads as bought.
- `QUOTE_STATUS_LOAD` in `services.py` selectin-loads the two collections for the queries whose results show status.
- `Quote.purchase_lists` and `Quote.purchase_orders` are now declared on `Quote`. The list side used to be a `backref`, which mypy could not see. That cleared the 3 mypy errors `services.py` had.

## 2. One price target (High)

After 0.2.x, `WatchlistService.create` rejects a missing `target_price`, so every watchlist row is a threshold. `price_alert` and `watchlist` now hold the same thing:

| | `price_alert` | `watchlist` |
| --- | --- | --- |
| product | `product_id` | `product_id` |
| threshold | `threshold_value` | `target_price` |
| currency | `threshold_currency`, default USD | `target_currency`, null means USD |
| on/off | `active` | `active` |
| fires | once, sets `triggered_at` | on every `check` run |
| text | - | `notes` |

`MonitorService.check` runs two loops. Each does the same `ForexService.to_usd` conversion and the same comparison, and they produce two message formats. The notification payload has `alerts` and `watchlist` keys.

The "fires" row is a behaviour bug. A daily cron job re-sends a met watchlist target every day. A met alert is sent once.

Change:

- One table, `price_target`: `product_id`, `threshold`, `currency` (not null, default USD), `active`, `created_at`, `triggered_at`.
- Fire once. Editing the threshold clears `triggered_at`, which re-arms the target.
- Free text moves to `note` rows on the product.
- One service, one `MonitorService` loop, one notification key.
- CLI: `alert` and `watchlist` become one noun, `watch` (`add|list|edit|off|rm`). TUI: Alerts and Watchlist become one tab.
- The path that adds a product to Considering (`watchlist add` with no target) moves to `purchase-list consider PRODUCT`.

Migration: copy `watchlist` rows into `price_target` with `triggered_at = NULL`. Copy non-empty `watchlist.notes` into `note` (`entity_type='product'`). Copy `price_alert` rows unchanged. Drop both old tables.

Done as proposed, plus:

- A 0.2.0 `watchlist` has no `target_currency`. `price_target_statements` reads the columns first and uses `'USD'` when it is missing.
- Rows for a deleted product would fail the foreign key. They are not copied.
- Target-less watchlist rows put their product's quotes on Considering.
- `run_migrations` skips a `DROP` once any earlier statement has failed. Before, a failed copy was followed by the drop.
- An exact duplicate active target (same product, threshold, currency) is rejected. Different thresholds on one product are allowed, as alerts allowed.

- Only `MonitorService.check` fires a target. `QuoteService.update_price`, the TUI price edit, used to call `PriceTargetService.check` itself. A target it fired had `triggered_at` set, so `check` never notified it. "Met" is now derived on read by `PriceTargetService.met_now`, and `triggered_at` means "notified". A `notified_at` column was the alternative. It would have stored two timestamps for one event.

## 3. Drop `quote.currency` (Low)

`QuoteService.create`, `ImportService.import_quotes_csv` and `ScraperService.create_quote_from_scrape` all write `currency="USD"`. The entered currency is in `original_currency`. `ensure_for_quote` reads `quote.currency or "USD"` and always gets USD.

Drop the column. Readers use the base currency (section 4) or `original_currency`. Ship it in the same migration as section 1.

Done. The claim above missed one writer. `Vendor.add_product` in `models.py` wrote `currency=self.currency` with the price unconverted. Only tests and the `models.py` `__main__` demo call it. `quote_currency_statements` keeps any value other than USD as a quote note before dropping the column. Exports keep their Currency column and write `USD`, so existing spreadsheets still line up.

Open: `Vendor.add_product` still stores the price it is given as `value`, which is USD by definition. For a non-USD vendor that value is wrong. It bypasses `QuoteService.create`, which converts the price and records history. It has no app caller. Delete it, or have it take a USD price.

Money is stored two ways. A quote stores the USD amount plus the entered amount. A purchase order stores the native amount plus `grand_total_usd`. Making both use one convention touches every price reader, so it is not proposed here.

## 4. One base currency per database (Done)

A database normalizes every amount to one base currency. Otherwise its amounts do not compare. Section 3 removed `quote.currency`, which held `"USD"` on every row. That column was not a way to change the base: no reader used it, and a base that varied per row would mix units in `value`.

The base is a fact about the database, so it is stored once, in the database:

- `setting` holds `base_currency`. `init_db` writes `USD` when the row is missing, so every database names its base.
- `buylog db init --base CODE` changes it only while no `quote`, `quote_history`, `purchase_order` or `forex` rows exist (`SettingService.set_base_currency`). Those are stored relative to the base.
- Configuration (an environment variable) was rejected. The same database file could then be read in a currency it was not normalized to.

Code that assumed USD now reads the base:

- `ForexService.to_usd` is `to_base`. `Forex.usd_per_unit` is `base_per_unit`, and `PurchaseOrder.grand_total_usd` is `grand_total_base`. The two columns are renamed in place by `rename_statements` in `migrate.py`.
- `ForexRefreshService` asks Frankfurter for rates against the base.
- A vendor, price target or imported row with no currency takes the base. A purchase order with no currency still takes its vendor's.
- `format_money` (`$` for USD, else the code) and `get_base_currency` in `models.py` format every base amount.

Not done:

- Changing the base after amounts exist. It would re-normalize every stored amount, and which rate to use (entry-time or current) is a decision nobody needs yet.
- Recording the entered currency on every quote. `original_value` / `original_currency` are still null when a price was entered in the base.

## Order

1 to 4 are done. `_drop_column_statements` in `migrate.py` is the shared pattern for the next column drop.
